# 工作流停止计划书（立刻停止 + 同步停止定期执行）

> 状态：已实现
> 关联代码：`app/controller/v1/browser_control/execution/workflow_router.py`、
> `app/services/execution/{cancellation,run_tasks}.py`、
> `app/services/execution/workflow/guards.py`、`app/services/execution/workflow_scheduler.py`

## 1. 背景与问题

上一版停止（`POST /workflows/runs/stop`）是「两阶段、协作式」：

1. `cancellation_registry.request_cancel(run_id)` 置标记；
2. 执行器只在**步骤边界**检查标记（`pipeline.py` 里 `scope.is_cancelled()`），
   因此一个长步骤（长 `wait`、整段 `loop`）会把停止拖到步骤结束才生效；
3. 超过 `workflow_stop_grace_seconds`（默认 30s）后，周期任务
   `enforce_stop_grace` 才 `task.cancel()` 强制终止。

同时，停止只作用于**当前这一次运行**：不触碰工作流的 `is_enabled` /
`trigger_config`，也不移除 APScheduler 的 cron 任务。若工作流是定时任务
（`trigger_type = "cron"` 且 `is_enabled = true`），下一个触发点会**再次自动拉起一次运行**，
用户表现为「点了停止，过一会儿自己又跑起来了」。

## 2. 目标

- **G1 立刻停止**：点击停止后立即中断本次运行，不再等步骤边界 / 宽限期；
- **G2 定期执行也停止**：停止工作流的同时关闭它的定时任务，后续 cron 触发不再启动运行；
- **G3 幂等**：重复点击停止不报错；已结束的运行仍按最终状态返回；
- **G4 语义清晰**：被停止的运行终态仍为 `cancelled`（不是笼统的 `interrupted`）。

## 3. 方案

### 3.1 立刻停止

`stop_workflow_run` 在「本实例有存活 task」分支里，先 `request_cancel`（保证收口时
状态改写为 `cancelled`），**紧接着**调用 `workflow_run_tasks.cancel(run_id)`
（即 `asyncio.Task.cancel()`），立即向执行协程抛出 `CancelledError`：

```
request_cancel(run_id)  →  收口语义 = cancelled
workflow_run_tasks.cancel(run_id)  →  立刻打断当前 await
```

`run_workflow` 的既有收口链路无需改动即可承接：

- `except BaseException` 捕获 `CancelledError` → 先按 `INTERRUPTED` 收口；
- `finally` 解除执行期标记、关闭本次运行自己打开的页面；
- 末尾 `if cancellation_registry.is_cancelled(...)` → 改写为 `CANCELLED`；
- `finish()` 落库、SSE 推终态、`cancellation_registry.clear()`。

保留 `enforce_stop_grace` 周期扫描作为兜底（例如未来出现「只置标记不 `cancel`」的调用方）。

### 3.2 定期执行同步停止

新增 `workflow_scheduler.disable_workflow_schedule(workflow) -> bool`：

1. 仅当工作流当前**确实有定时执行**（`is_enabled = true` 且 `trigger_type = "cron"`
   且 `trigger_config.cron` 可解析）时才动作，否则返回 `False`（幂等）；
2. `workflow_crud_svr.update(id=..., is_enabled=False)` 落库；
3. `sync_workflow_job(model)` → `is_schedulable` 为假 → `remove_workflow_job()` 移除
   APScheduler 任务并把 `next_run_at` 清空。

**为什么改 `is_enabled` 而不是只 `remove_job`**：调度任务在服务启动
（`register_all_workflow_jobs`）与任意工作流 `update` 时都会按 `is_enabled` 重新注册，
只删 job 会在重启 / 保存后「复活」。

### 3.3 同工作流的其它运行

「停止」针对的是**这个工作流**，不只是调用方传来的那一条 `run_id`：多选浏览器
（`browser_ids`）、并发（`concurrent_exec`）、定时触发都可能同时存在多条记录，
只停一条其余继续跑，用户看到的就是「停止没生效」。

`workflow_run_crud_svr.list_active_of_workflow()` 取出同工作流的 `QUEUED` / `RUNNING`：

- `QUEUED` → `finish_queued(CANCELLED)`；
- `RUNNING` 且本实例有存活 task → `request_cancel` + `task.cancel()`；
- `RUNNING` 但无存活 task（僵尸）→ 复用 §3.4 的统一收尾。

配套防护：串行多浏览器循环（`launcher.run_sequentially`）在启动下一个浏览器前
会检查记录状态，`CANCELLED` 直接 `continue`；`_open_run` 若发现 `run_id` 对应记录
已被取消，直接抛 `WorkflowRunnerError`，绝不新建 `RUNNING` 记录把已取消的运行复活。

### 3.4 收尾复用「任务结束收尾」

停止路径不另写清理逻辑，统一复用 `launcher.finalize_run_after_task(run_id)`——
它原本是 task 的 `done_callback` 里的幂等补收口，现在扩展为**一次运行结束后的唯一收尾入口**：

1. 清理运行 task 句柄；
2. 记录仍为 `RUNNING` → 补收口为 `INTERRUPTED`；
3. 清掉会话上残留的执行期标记（否则该浏览器再也启动不了工作流）；
4. 清掉取消标记。

调用方：
- task 结束 → `_on_run_task_done` → `finalize_run_after_task`；
- 停止接口「跑着」的情形 → 只负责 `request_cancel` + `task.cancel()`，收尾由 task 结束时走同一函数；
- 停止接口「僵尸记录 / 同工作流僵尸运行」→ 直接 `await finalize_run_after_task(run_id)`。

### 3.5 接口响应

`POST /api/v1/rpa/browser/control/workflows/runs/stop` 响应由裸 `dict` 改为
`WorkflowRunStopResponse`（项目规范：禁止 `dict` 类型提示），字段：

| 字段 | 说明 |
|---|---|
| `run_id` | 运行ID |
| `status` | 该运行当前/最终状态 |
| `stopping` | 是否已下发停止（立刻中断） |
| `forced` | 是否直接 `task.cancel()` 强制中断 |
| `already_finished` | 运行此前已结束（幂等返回） |
| `queue_cancelled` | 该运行当时在排队，已被取消 |
| `reaped` | 僵尸记录被清理 |
| `schedule_stopped` | 本次是否关闭了该工作流的定期执行 |
| `cancelled_runs` | 被一并停止的同工作流其它 run_id 列表 |

## 4. 影响面与风险

- **原子操作被打断**：强制 `cancel()` 可能落在一次 Playwright `await` 中间，
  浏览器页面可能处于中间态。既有 `finally` 会关闭本次运行自己开的别名页，
  `main` 页保留，由空闲生命周期回收；这是「立刻停止」的必然代价。
- **`cancelled` 判定依赖 `request_cancel` 先于 `cancel`**：顺序不能反，
  否则收口会被判成 `interrupted`。
- **副作用变化**：停止现在会**停用工作流**（`is_enabled = false`），前端卡片开关会变为
  「已停用」，需要重新启用才能继续定时。这是需求「定期执行也停止」的直接结果。
- **前端 SDK**：响应模型变更需重新生成 `hey-api` SDK；前端封装已用本地类型 +
  `as any` 兼容，未生成前不会编译失败。

## 5. 前端调整

`WorkflowManagement.vue`：

- 停止前 `ElMessageBox.confirm` 明确提示「立即停止 + 关闭定期执行」；
- toast 文案改为「已停止当前运行」，并在 `schedule_stopped` 为真时追加「并已关闭定期执行」。

## 6. 验证清单

1. 静态：`python -m compileall app` / 导入路由无异常；`check_schemas` 通过；
2. 手动运行中点击停止：
   - 运行记录**立即**变为 `cancelled`（不等步骤边界、不等 30s）；
   - 本次运行打开的别名页被关闭，`main` 保留；
   - SSE 收到终态帧，前端卡片恢复「立即运行」；
3. 定时工作流（cron + enabled）运行中点击停止：
   - 运行立刻 `cancelled`；
   - 工作流 `is_enabled` 变 `false`，APScheduler 中 `workflow:{workflow_id}` 任务被移除，
     `next_run_at` 清空；
   - 到下一个 cron 触发点**不再**启动新运行；重启服务后也不会被重建；
4. 幂等：运行已结束后再次停止 → `already_finished = true`，不报错；
5. 多运行场景：同工作流有多条 `queued` / `running` 运行时停止 → 全部收口为
   `cancelled`，`cancelled_runs` 返回其 run_id；串行多浏览器不会再启动下一个；
6. 复活防护：把某条 `queued` 记录手工置 `cancelled` 后再执行该 run_id →
   `_open_run` 抛 `WorkflowRunnerError`，记录保持 `cancelled`（不会被改成 RUNNING）。
