# 多页面并行执行计划书

> 状态：**已实施（2026-10-21 多页面 + 并行分支；2026-10-22 改为「多工作流并行」语义）**
> 版本变更：原先「同一浏览器多工作流按 FIFO 串行排队」已废弃，改为
> **同一浏览器上多个工作流并行执行，各自使用独立页面**；页面总数受
> `browser_max_pages_per_context` 限制，达到上限时 `open_page` **等待空位**。

## 背景

工作流执行原本固定绑定一张页面：`run_workflow` 在执行开始时
`page = get_current_page()`，之后所有步骤复用该对象；且同一浏览器同一时刻
只允许一个工作流执行（`entry.workflow_run_id` 单值互斥 + `_precheck` 的
RUNNING 检查 + per-browser 运行队列）。

新的目标：

1. **G1** 同一浏览器上**多个工作流并行执行**（取消浏览器级串行互斥）；
2. **G2** 页面用**别名**标识（`open_page(name=...)`），步骤显式声明在哪个页执行；
3. **G3** 页面总数达到 `browser_max_pages_per_context` 时**等待空位**
   （不关闭任何已有页面），可配置等待超时；
4. **G4** 运行结束只关闭**本次运行自己打开的页面**，不关浏览器（浏览器交给
   既有空闲生命周期回收）。

## 1. 语义模型（本次修订核心）

| 维度 | 旧（已废弃） | 新 |
|---|---|---|
| 多工作流 | 同浏览器 FIFO 排队，一次只跑一个 | **并行**，N 个工作流同时跑 |
| 互斥依据 | `entry.workflow_run_id` 单值 + `_precheck` 拒绝 RUNNING + `run_queue` | 取消；仅保留「执行期拒绝调试类接口」 |
| 页面隔离 | 无（都挤在 main） | 每个运行 `open_page` 自己的别名页 |
| 资源上限 | 队列长度（隐式） | **页面数**；满了 `open_page` 等空位 |
| 运行结束 | 回收浏览器 | 只关自己开的页 |

`WorkflowRunStatusEnum.QUEUED` 与 `run_queue.py` 保留（兼容历史数据 / 备用），
但**不再参与运行互斥**：`run_workflow` 不再 `acquire` 执行权。

## 2. 页面别名与生命周期

### 2.1 注册表（`app/services/RPA_browser/session/page_registry.py`）

```
PageRegistry（按 (mid, browser_id)）:
  entries: dict[alias, PageEntry]     # PageEntry(page, owner_run_id, opened_at)
  capacity  = settings.browser_max_pages_per_context
  condition = asyncio.Condition       # 满时等待 / 释放时唤醒
```

- 别名作用域 = **整个会话**（跨运行唯一）：两个并行运行若用同名别名会冲突
  （报「页面别名已存在」），因此每个运行必须用**不同别名**；
- 默认别名 `main`：运行开始时绑定会话当前页，`run` 不拥有它，结束时不强关；
- 容量统计的是 context 下**实际存活页面数**（含未登记的、用户手动开的页）。

### 2.2 动作

| 动作 | 语义 |
|---|---|
| `open_page` | `name`/`url`/`wait_until`/`nav_timeout`/`acquire_timeout`；满则等待，超时报「等待空闲页面超时（N/M 已占用）」 |
| `close_page` | 关指定别名页并唤醒等待者；`main` 不可关；不能关别的运行拥有的页 |
| `new_page`（旧） | **删除「满了关最旧页」逻辑**，改为明确报错并提示改用 `open_page` |

### 2.3 页面身份（botright 修复）

`botright` 的 `BrowserContext.pages` 每次访问都新建 `Page` 包装对象，导致
`all_pages[i]` 与 `new_page()` / 注册表里保存的页面**不是同一对象**，
任何按对象身份的判断都会失效（如「这个页面被工作流占用吗」恒为否）。

已修 `botright/playwright_mock/browser.py`：按底层 impl（`_page._impl_obj`，
跨包装稳定）**缓存 Page 包装**，`new_page()` 产出的包装也登记进同一缓存。
此后 `all_pages[i] is new_page_result` 成立，注册表的身份比较才可靠。

### 2.4 建页语义（工作流 / 手动统一）

任何建页路径（`open_page` 动作、`/operation/open_page` 手动新建）容量满时：

1. **优先回收未被工作流引用的页面**（无别名的页，如用户手动打开的）；
2. 没有可回收页时**阻塞等待空位**（`acquire_timeout`，默认 60s）；
3. **绝不关闭别名页**（工作流正在用的页）。

手动关闭页面（`/operation/close_page`、`/pages/close`）前会反查别名，
被工作流引用则拒绝关闭并提示先停止对应工作流。

### 2.5 步骤级页面引用

`BaseActionParams.page: str | None`——空 = `main`。
engine 在创建动作前解析：`params.page` 有别名 → 从注册表取 Page，取不到返回
可读错误「页面 X 不存在或已关闭（请先 open_page 或检查别名）」。

## 3. 多工作流并行

- `launch_workflow_run`：仍是「立即返回 run_id，后台 task 执行」，但**不再串行排队**；
- `run_workflow`：删掉 `run_queue.acquire/wait_turn`，删掉 `_precheck` 里
  「同浏览器已有 RUNNING 运行就拒绝」的检查；
- 会话执行期标记改为**集合**：`live_service.active_workflow_runs: set[str]`
  （`begin_workflow_run` 为 `add`，`end_workflow_run` 为 `discard`），
  `is_workflow_running` = 集合非空 → 执行期仍拒绝调试类接口（直播只读不受影响）；
- 各运行的 `execution_id`（= run_id）独立，日志 / 进度 / 计费 / 停止互不影响；
- `main` 页被多个并行运行同时读写是**允许但危险**的：动作 JSON 应确保并行分支
  / 并行运行各自 `open_page`，不要共用 `main`（Playwright 层不会报错，但会互相干扰）。

## 4. 运行结束清理

`run_workflow` 的 `finally`：

1. `end_workflow_run`（集合移除本次 run_id）；
2. `page_registry.close_owned((mid, browser_id), run_id)` —— 只关本运行开的页；
3. 浏览器**不回收**（`workflow_release_browser_after_run` 默认 `False`），
   由 `_check_session_cleanup` 的 idle 阈值驱动关闭；
4. `ExecutionEngine.execute_action / execute_steps` 的 finally 也做一次
   `close_owned(exec_id)`（幂等），覆盖单动作 / 内联调试执行。

## 6. 验证

1. **并行运行**：N 个工作流同时触发 → 全部 `running`（不再排队），
   各自 `open_page` 不同别名并操作自己的页；
2. **页面满则等待**：容量 M，第 M+1 个 `open_page` 阻塞等待；前序运行
   `close_page`（或结束自动关页）后立即放行；超时报可读错误；
3. **不误关页**：等待期间浏览器里的页面数**不减少**；
4. **运行结束**：本运行开的页被关，`main` 与浏览器保留；
5. **兼容**：不含 `page` 参数的既有动作 / B 站抽奖动作行为不变；
   同一浏览器同时只能有一个「执行期」用于拒绝调试接口。
