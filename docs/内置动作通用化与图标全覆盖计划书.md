## 1. 背景与问题

1. `bili_reserve` 是唯一被登记为「内置动作」的 B 站业务动作：`app/services/execution/actions/bili.py`
   整文件是站点专属 DOM 流程；参数模型 `BiliReserveParams` 的 docstring
   「参与 B 站空间预约抽奖参数 - DOM 流程」会作为 `json_schema.description`
   出现在工具箱「基础操作」的悬浮说明里。这与「内置动作必须通用」的硬约束冲突。
2. `get_window` 动作实际行为是**读取 `window` 对象上某个属性 / 某个对象的字段**（`GetWindowParams.property_path`
   / `object_name`，禁止函数调用），但面板显示名是「获取窗口」，容易被误认为「切换 / 获取浏览器窗口」。
3. 动作图标未全覆盖：后端 `BuiltinActionIconId` 只登记 28 个编号，`open_page` / `close_page` / `parallel`
   无编号；`notify=90` 被标注「未占用」；`press` / `wait_for_response` / `element_state` /
   `select_option` / `wait_for_url` 使用 124~128 号，而图库 `s_33` 实际只有 `1..121`。
   自定义动作 `ca_*` 未选图标（`0/0`）时前端回落 `QuestionFilled`。

用户确认的口径：

- 「基础操作」中的 B 站预约抽奖：**彻底移除内置动作**，并把 DOM 流程改写成通用动作 JSON 步骤，同步数据库并实跑验证。
- 前端所有 action：**图库图标全覆盖**（后端补齐真实存在的 `s_33` 编号；前端给自定义动作自动分配默认图库图标，消除问号/兜底）。

## 3. 硬约束

1. `app/services/execution/actions/**` 内不得出现站点名 / 域名 / 站点选择器 / 业务资源类型分支；
   站点选择器、业务判断、重试次数全部落在 `actions/*.json` 的步骤参数、`if_else`、`loop`、`on_error` 里。
2. JSON 是唯一可读源头：**先改 JSON、再同步 DB**，源动作与 Fork 都要更新；同步前备份 JSON，同步后回读比对。
3. 落库前静态校验：`workflow_step_adapter.validate_python` + `PipelineBuilder.build`；
   落库后在 RPA-Browser 项目内实跑一次相关工作流（测试工作流），运行记录 / 变量结果要对得上。
4. 类型注解禁止 `dict` / `Dict[str, Any]`，一律 pydantic / dataclass；Python 3.13 写法；import 全在文件头。
5. 前端：不写 `<style>`、不用 `:style`、不用 Element Plus 图标充当业务图标；动作图标走
   `action-icons/` 图库（内容图库例外，见 `docs/rpa-自定义动作图标计划书.md` §5.1）。

### 4.2 预约抽奖 DOM 流程 → 通用步骤（写进 `action_104682832_参与B站抽奖.json`）

原步骤（外层 `loop` 遍历 `reserve_data.items`，循环变量 `rs_item`）：

```json
{"action_id": "bili_reserve", "params": {"reserve_sid": "{{rs_item.reserve_sid}}", "reserve_url": "{{rs_item.reserve_url}}"}, "output_vars": ["rs_value","rs_joined","rs_already","rs_found"]}
```

替换为**通用动作序列**（站点选择器只出现在 JSON 参数里）：

1. `print` + `input_vars`：每轮重置 `rs_value/rs_joined/rs_already/rs_found/rs_card_count/rs_joined_count/action_reserve`。
2. `navigate`：`mode=goto`、`url={{rs_item.reserve_url}}`、`wait_until=domcontentloaded`、`on_error=continue`。
3. `wait`：`selector=.subscribe-section-warp`、`state=attached`、`timeout=15000`（超时仍成功，天然是探针）。
4. `element_state`：`kind=count` → `output_vars=["rs_card_count"]`。
5. `if_else` `expression: rs_card_count > 0`：
   - True：`print` 置 `rs_found=true` → 内层 `loop`（`fixed_count=3`，
     `break_condition` = `rs_joined == true`）执行「检查已预约 → 点击 → 校验 → 重试」：
     - `element_state` 统计 `[data-sid]` 卡片内「已预约」按钮数 → `rs_joined_count`；
     - `if_else rs_joined_count > 0` → True 分支 `print` 置
       `rs_joined/rs_value/rs_found/rs_already=true`、`action_reserve=已预约`；
     - False 分支：`click` 卡片内 `button.btn`（`on_error=continue`，`input_vars` 置 `rs_already=false`）
       → `wait` 等「已预约」按钮 `4000ms` → `element_state` 再统计 →
       `if_else rs_joined_count > 0` 置成功变量 → `wait` 固定 `1000ms` 冷却。
   - False：`print` 记录「未找到预约模块 / 卡片」。

变量契约与下游不变：`rs_joined` 仍由原有 `if_else` 判定 `mark_resource_result` 成功/失败，
`rs_already` / `rs_found` / `action_reserve` 仍由原有 `print` 汇总输出。

> 语义差异（可接受）：原内置动作在页面不提供 `data-sid` 时会退化到「第一张未参与卡片」；
> JSON 版统一按 `data-sid` 精确定位（RPC 数据必带 `reserve_sid`）。重试次数、校验超时、
> 冷却间隔均与原参数默认值一致（3 次 / 4000ms / 1000ms）。
