# 用户提交报错与实时推送服主计划书

## 1. 背景与目标

现状：RPA 后端**没有**「用户主动提交报错 / 反馈给服主」的专用接口。相关能力都不同用途：

- `report_webrtc_visibility`：浏览器可见性上报，连通性诊断；
- `approval/submit`：公开动作/工作流的**审批**，不是运行报错；
- `reports_count`：动作/工作流被举报计数，无对应用户接口；
- 调试类（`validate_steps` / `get_run_logs` / `execute_action`）只查/试跑，不回传错误。

目标：新增一个「提交报错 / 反馈」接口，让用户（含 LLM 通过 MCP）把**运行出错的现场**直接告诉服主，服主实时收到通知，用于及时定位问题、改进设计。

决策（已与用户确认）：

- **落库 + be-message 推送**：错误报告必落库，同时通过 be-message 实时推送服主（邮件/Webhook 等渠道）。
- **顺带加前端提交入口**：普通用户不用 MCP 也能提交。

## 2. 总体设计

```
用户 / LLM(MCP)
   │  POST /api/v1/rpa/browser/feedback/submit
   ▼
feedback_router  ──►  RpaErrorReport 落库
   │                        │
   │                        └─► notify_owners() 弱依赖双通道推送
   │                              ├─ 站内系统通知 publish_notify(服主mid)（be-message，实时）
   │                              └─ 外部推送 push_msg.send_error(服主NotificationConfig)（邮件/Webhook）
   ▼
返回 report_id + notified
```

关键取舍：

- **MCP 自动暴露**：接口落在用户级 router（`browser`），`app/mcp/exposure.py` 的 `build_user_app()` 会自动按 OpenAPI 转成 MCP 工具，**无需改 MCP 代码**；工具名会被 `shorten_tool_names` 压成 `rpa_feedback_submit`。
- **服主 mid 来源**：RPA 不持有管理员表（管理员在 be-message 的 `msg_admin`），故用配置项 `feedback_notify_mids`（逗号分隔服主 mid）指定推送目标；为空则**仅落库不推送**。
- **推送是弱依赖**：落库已成功即返回 `notified`，推送失败只 `logger.warning`，绝不向上抛、不阻塞提交。
- **幂等标题**：站内通知在 be-message 侧按 `(target_value, title)` 判重，标题携带 `report_id` 区分不同报告。

## 3. 数据模型

新增 `app/models/database/feedback/models.py`，`RpaErrorReport(table=True)`，继承 `BaseSQLModel`（自带 `created_at`/`updated_at`）：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | `int` PK autoincrement | 主键 |
| `report_id` | `str` unique index | 报告唯一标识（雪花），供通知幂等 |
| `mid` | `str` index BIGINT | 提交者 mid |
| `category` | `str` | `bug` / `suggestion` / `other` |
| `title` | `str` | 简短标题 |
| `description` | `Text` | 详细描述（错误现象 / 期望） |
| `context` | `Text` | 错误上下文 JSON（source/action_id/workflow_id/run_id/browser_id/error_message/error_detail/page_url/extra） |
| `status` | `str` | 处理状态，`pending` / `resolved` / `ignored`（默认 `pending`，服主后台处理） |

模型必须在**三处** import 以注册到 `SQLModel.metadata`：

1. `alembic/env.py`（建表 metadata 来源）
2. `app/utils/alembic_migration.py`（`check_schemas()` 校验用 metadata）
3. `test/conftest.py`（测试 `create_all`）

新增 alembic migration `alembic/versions/20261031_rpa_feedback_report.py`（`down_revision = '20261031_wf_notify_channels'`）建 `rpaerrorreport` 表。`check_schemas()` 会校验「模型声明但数据库不存在的表」为 critical，缺 migration 会拒绝启动，故必须配齐。

## 4. 接口设计

路由注册（参照 notification 模块）：

1. `app/models/router/router_prefix.py`：加 `BrowserFeedbackRouterPath`（`submit = "/feedback/submit"`、`list = "/feedback/list"`）；
2. `app/models/router/router_tag.py`：加 `RouterTag.browser_feedback = "报错反馈"`；
3. `app/models/router/all_routes.py`：加 `browser_feedback_router = RouterInfo(...)` 并入 `ALL_ROUTERS` 的 browser 子列表；
4. `app/controller/v1/browser/base.py`：加 `new_feedback_router()`；
5. `app/controller/v1/browser/__init__.py`：`include_router(feedback_router)`。

### 4.1 提交报错

`POST /api/v1/rpa/browser/feedback/submit`（`browser_feedback` tag，`prefix=/browser`）

请求 `FeedbackSubmitRequest`（`app/models/feedback/feedback_requests.py`，扁平字段便于 LLM 填写）：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `category` | 否 | `bug` / `suggestion` / `other`，默认 `bug` |
| `title` | 是 | 简短标题 |
| `description` | 是 | 详细描述 |
| `source` | 否 | `mcp` / `web`，来源标记 |
| `action_id` | 否 | 相关动作 id |
| `workflow_id` | 否 | 相关工作流 id |
| `run_id` | 否 | 相关运行记录 id |
| `browser_id` | 否 | 相关浏览器 id |
| `error_message` | 否 | 错误摘要 |
| `error_detail` | 否 | 错误详情 / 堆栈 / 失败步骤 |
| `page_url` | 否 | 出错时页面 URL |
| `extra` | 否 | 其他键值对（dict） |

响应 `FeedbackSubmitResp`：`report_id`、`mid`、`created_at`、`notified`（是否已推送服主）。

`mid` 从 `get_auth_info_from_header` 取，服务端回填，**不接受用户传 mid**。

### 4.2 查询反馈（辅助，供 LLM 查历史）

`GET /api/v1/rpa/browser/feedback/list`：查询当前用户自己的反馈列表（分页，`BasePaginationReq`/`Resp`）。让 LLM 能「查一下我之前提交过什么、哪些已处理」。

## 5. 推送方案

新增 `app/services/feedback/feedback_service.py`：

- `create_report(...)`：落库 `RpaErrorReport`，返回 `report_id`。
- `notify_owners(report, mid)`：弱依赖，对每个服主 mid 双通道投递：
  - **站内系统通知**：`publish_notify(服主mid, title, content, jump_url="/app/rpa-browser/feedback")`；标题带 `report_id` 保证幂等；`level` 用 `NotifyLevelEnum.WARNING`。
  - **外部推送**：`BrowserService(服主mid).get_notification_config(session)` 拿服主的 `NotificationConfig`，若配置了渠道则 `push_msg.send_error(content, subject="用户报错反馈", conf=config, mid=服主mid)`（邮件/Webhook 等）；未配置则跳过站内通知兜底。
  - 两者独立、均 try/except，失败只 `logger.warning`。

通知正文由 `_report_notify_content(report)` 组装：标题、分类、提交者 mid、关联 action/workflow/run/browser、错误摘要、错误详情、页面 URL。

配置项（`app/config.py` 的 `Settings`）：

```python
# 服主 / 管理员 mid 列表（逗号分隔）：用户提交报错后实时推送的目标。
# 为空则仅落库不推送。示例：RPA_FEEDBACK_NOTIFY_MIDS=123,456
feedback_notify_mids: str = ""
```

提供 `settings.feedback_notify_mid_list` 属性解析为 `list[int]`。

## 6. 前端设计

前端需求文档：`docs/frontend_requirements/rpa_feedback_submit.md`（Vue3 项目侧）。

- 新组件 `src/components/rpa-browser/FeedbackSubmitDialog.vue`：反馈提交弹窗（分类、标题、描述、错误上下文折叠区、自动带上 action/workflow/run/page_url）。
- 入口：RPA 页面侧边 / 调试框「提交反馈」按钮（普通用户与 LLM 共用同一后端接口）。
- 调用同一 `POST /api/v1/rpa/browser/feedback/submit`；提交成功提示「已提交并通知服主」。
- 样式遵循项目规范：Tailwind 原子类 + `theme.css` 语义色，无 `<style>` 块、无内联样式；外链跳转走 `linkPolicy`（本页无外链）。

## 7. MCP 暴露

无需改 MCP 代码。接口在用户 router，`build_user_app()` 自动纳入：

- 工具名：`shorten_tool_names` 压成 `rpa_feedback_submit` / `rpa_feedback_list`。
- 工具描述来自路由 `summary` + `description` + 请求模型 `Field(description)`，清晰标注「提交运行报错/反馈给服主」，让 LLM 知道何时调用。
- 校验：`.venv/bin/python -m app.mcp --selftest` 确认工具清单含 `rpa_feedback_submit`。

## 8. 边界与约束

- **鉴权**：走网关注入的 `get_auth_info_from_header`，`mid` 服务端回填；MCP 通道有 `BanGuardMiddleware`，封禁用户不能借 MCP 绕过。
- **仅落库不推送**：`feedback_notify_mids` 为空或推送失败，仍返回成功（`notified=false`），提交本身不丢。
- **内容校验**：`title`/`description` 必填非空；`category` 限定枚举；`extra` 序列化为 JSON 存 `context`。
- **上下文体积**：`error_detail` 存 `Text`，不截断；推送正文对超长内容截断（避免通知过长），完整内容看库。
- **SQLModel 创建时机**：数据库模型在 `app/models/database/feedback/models.py`，请求/响应模型在 `app/models/feedback/`。
