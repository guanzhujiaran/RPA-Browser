# 通知动作与运行告警计划书

## 背景

通知**通道**已经存在（`app/services/execution/workflow/notify.py` 双通道）：

1. 站内系统通知：`publish_notify()` → be-message `msg_notify`（无需用户配置，只受 `recv_notify` 开关约束）；
2. 外部推送：`push_msg.send()`（PushMe / PushPlus / webhook），读用户全局 `NotificationConfig`，
   `push_enabled` / 免打扰由 be-message 投递侧统一拦截。

但触发点只有运行开始 / 结束（`notify_on_start` / `notify_on_end`），正文只有步骤计数与失败原因。
两类问题用户完全收不到提醒：

- **运行中持续降级**：例如 LLM Key 失效（401）、免费额度用尽（429 `free-models-per-day`），
  动作被 `on_error=continue` 容忍后工作流照常跑完，只在日志里有记录；
- **工作流内的业务级告警**：动作 JSON 里判断出「该换 Key 了」「该补额度了」，却没有任何「发通知」的能力。

本计划补充两件事：

- **A. 运行结束通知里加「运行告警」汇总**：把被容忍的失败聚合成一段告警文案，零新增通道、零新增动作；
- **B. 通用 `notify` 内置动作**：让动作 JSON 自己按条件触发通知，并带去重（否则一次运行几百次失败会刷屏）。

---

## A. 运行结束通知的「运行告警」段

### A1. 采集（`WorkflowRunProgressReporter`）

`on_error=continue` 容忍的失败在 `Pipeline` 里被标 `ActionResult.tolerated=True`
（该标记现已随 `results_data` 一起返回，用于区分「致命失败」与「显式容忍」）。
容忍计数的口径在上报器里统计——它能看到**所有层级**的步骤终态
（`step_finished` / `body_step_finished` 都带 `result`），而顶层 `results_data` 只有一层：

- `tolerated_count: int` —— 被容忍失败的步骤数；
- `tolerated_samples: list[str]` —— 前 3 条**去重后**的错误摘要（每条截断 200 字）。

### A2. 传递（事件摘要）

`WorkflowRunSummary` 增加上述两个字段，由 `run_workflow` 从上报器读取后随终态事件下发；
`run_event_handlers.notify_run_finished` 把它们塞进 `_notify_run(summary=...)`。

### A3. 渲染（`_run_notify_content`）

仅当 `tolerated_count > 0` 时追加：

```
运行告警：3 个步骤失败但已容错继续
循环统计：循环「批量点赞」执行 18/20 轮、体内 成功 54/失败 6
  - [LLM(llm)] Error code: 429 ... free-models-per-day
  - ...
提示：这类失败不改变运行结论（成功），但可能已降级执行，请检查配置。
```

「循环统计」行来自 `WorkflowRunSummary.loop_summaries`（见 D4），经
`render_loop_summaries` 统一渲染；无循环时该行不出现。执行结果行（成功/失败/共 N 步）
只数顶层步骤，与循环统计是两个维度，互相不覆盖。

不改标题、不改通道、不改开关：仍然受「结束」时机的通道开关（`notify_inbox_on_end` /
`notify_push_on_end`，见 E 节）与用户推送设置约束。

## B. 通用 `notify` 内置动作

### B1. 参数（`NotifyParams`）

| 参数 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `title` | `str` | 必填 | 通知标题（≤200 字，支持 `{{变量}}`） |
| `content` | `str` | `""` | 通知正文（≤4000 字，支持 `{{变量}}`） |
| `level` | `NotifyLevelEnum` | `NORMAL` | 1 普通 / 2 重要 / 3 紧急，决定外部推送主题 `[i]/[w]/[f]` |
| `jump_url` | `str \| None` | `None` | 站内通知跳转地址 |
| `channel` | `"both" \| "inbox" \| "push"` | `both` | 投递通道 |
| `dedupe_key` | `str \| None` | `None` | 去重键（缺省用 `title`）；同一 key + `mid` 命中当天记录则跳过 |
| `once_per_day` | `bool` | `True` | 按服务时区（`settings.app_timezone`）自然日去重 |

### B2. 结果（`NotifyResult`）

| 字段 | 说明 |
|---|---|
| `deduped` | 是否因去重被跳过 |
| `inbox_sent` | 站内通知是否投递成功 |
| `push_sent` | 外部推送是否投递成功 |

### B3. 实现要点

- 通道复用既有实现：`publish_notify` / `push_msg.send`，与运行通知同一套用户开关语义；
- **弱依赖**：任一通道异常只记 warning，动作本身仍返回成功（除了去重跳过，不因通知失败中断工作流）；
- 去重表是进程内 `dict[(mid, dedupe_key)] = 日期`，按自然日切换自动失效；
  多实例部署时去重不跨进程（可接受：通知本身幂等，最坏是多一条）；
- 与站点/业务无关：只处理「发通知」这一机制，业务判断留在动作 JSON 的 `if_else` 里。

### B4. 使用方（`参与B站抽奖`）

在 LLM 失败的 `on_error_branch` 里，按错误类型各发一条（均 `once_per_day=true`）：

- `'Error code: 401' in last_error or 'invalid api key' in last_error`
  → `URGENT`「LLM Key 失效，请更换」；
- `'free-models-per-day' in last_error`
  → `IMPORTANT`「LLM 免费额度已用尽」；
- `'Error code: 429' in last_error`（其余限流）
  → `NORMAL`「LLM 被限流，已自动回退抄评论」。

去重键分别固定为 `llm_key_invalid` / `llm_quota_exhausted` / `llm_rate_limited`（按工作流 + 天去重）。

## 兼容性与边界

- `notify` 是**新增**动作类型，存量 JSON 不含它，反序列化不受影响；
- `WorkflowRunSummary` 新增字段都有默认值，历史运行记录与旧事件无需迁移；
- 运行告警只统计「被容忍的失败」，默认不改变运行结论（仍是 success），也不改 `failed_count`；
  仅当容忍条数达到熔断阈值（见下节）时才降级为 failed；
- 前端动作面板按 `BuiltinActionType` 枚举自动展示新动作，参数表单按 `NotifyParams` 渲染。

## D. 失败可见性三原则（2026-10-25 补充）

起因：一次抽奖运行「循环都在跑、什么都没做、也没有 error」。根因不是动作不报错，
而是三层容器把它**静默降级**了。结论是三条原则，改动都落在控制流层，动作层语义不变。

### D1. 失败必须默认可见

| 容器 | 默认 `on_error` | 说明 |
|---|---|---|
| 普通步骤（atomic） | `stop` | 一直如此 |
| `if_else` | `stop` | 一直如此 |
| **`loop`** | **`stop`（本次由 `continue` 改）** | 旧默认值硬编码在 `PipelineBuilder` 里、且不体现在动作 JSON，作者看不见 |

批量容错（一条失败继续下一条）必须**显式**写 `"on_error": "continue"`。存量动作
`action_104682832_参与B站抽奖.json`（4 个 loop）与 `action_weibo_转发抽奖.json`（1 个 loop）
已补齐显式声明，行为与迁移前一致；新增循环必须自己表态。

### D2. 容忍必须留痕（结论可以是成功，但痕迹不能为空）

1. `LoopStep` 在有被容忍失败时，`ActionResult.error` 不再是 `None`，而是
   `"N 个动作失败已按 on_error=continue 跳过；首个错误: ..."`，同时 `data` 里带
   `failed_steps / first_error / first_failed_action`；
2. `Pipeline` 成功步骤也会把 `result.error` 作为展示用 error 上报（`step_finished` /
   `body_step_finished` 的 `error` 字段），运行消息里能看到「成功但降级」；
3. 循环级 `continue` 在标记 `tolerated` 后补登运行告警（`record_tolerated`），否则
   `tolerated_samples` 永远为空；
4. **失败强制写操作日志**：`engine._run_action` 以 `force=not result.success` 调
   `save_action_log`，即使动作 / 工作流关了日志（或被 `workflow.log_enabled` 压制）
   也一定落一条记录——日志开关只控制「成功」的记录量，不能连失败一起吞掉。

### D3. 容器内动作必须上报

`IfElseStep` 执行分支体时固定传 `body_of_loop=True, nested_body=True`：

- 分支内的点击 / 输入 / 发送等动作会出现在运行消息里（此前只有循环体顶层那几步可见，
  失败也无从定位）；
- `nested_body` 让上报层级 +1，只发消息、**不占用**循环的第二条进度条，也不计入
  顶层 `completed_steps`；顶层 `if_else` 的分支体不在循环里，消息不带「第 N 轮」前缀。

### D4. 容忍上限熔断

`settings.workflow_tolerated_fail_failed_threshold`（默认 10，0=关闭）：一次运行中
被 `on_error=continue` 跳过的失败步骤数达到阈值时，即使顶层步骤全成功，运行结论也
降级为 `failed`，`error_message` 写明条数与示例，避免「跑 200 条失败 190 条仍报成功」。

**熔断文案必须带全量上下文**（否则用户只看到「N 次失败被跳过」，不知道整体干成了多少，
而熔断的主场景——批量循环容错——恰恰是顶层只有 1 个步骤、步骤计数毫无信息量的场景）：

- 步骤级：`步骤成功 {success_count}/{total}，N 次失败被容错跳过（熔断阈值 M），判定为失败`。
  措辞是「**次**」不是「步」——`tolerated_count` 统计所有层级（含循环体内动作），
  与只数顶层步骤的 `success_count/failed_count` 不同口径，写「步」会自相矛盾；
- 循环级：新增 `LoopRunSummary`（`app/models/runtime/workflow_progress.py`），
  `WorkflowRunProgressReporter` 在 `loop_finished` 时按层固化聚合（循环名、执行轮次 /
  计划轮次、体内动作成功/失败数）。体内动作归「上报时 ≤depth 的最近循环层」，
  分支体（if_else）动作归外层循环。`loop_finished` 消息文本里早有「执行 2/35 轮」，
  但那是消息不是聚合，错误文案与通知里拿不到，因此补此埋点；
- 渲染统一走 `render_loop_summaries`：同名循环多次实例化（嵌套循环里内层每轮都重跑）
  合并为一条、轮次求和；只有单次实例化才显示「执行 N/M 轮」，多次只显示「执行 N 轮」，
  不伪造分母；
- 传递：`WorkflowRunSummary.loop_summaries`（带默认值，旧事件可读），
  `run_event_handlers` 随 summary 字典下发，通知与熔断文案共用。

## E. 运行通知「通道 × 时机」矩阵（2026-10-31）

### E1. 问题

`notify_on_start` / `notify_on_end` 是**通道混合**的两个开关：置 true 时站内与站外同时发，
用户无法表达「站内留档、但别推到手机」，也无法表达「开始只想收站内、结束才推手机」。

### E2. 目标

把开关拆成 2×2 四象限：行 = 通道，列 = 时机。

| | 开始 | 结束（成功 / 失败 / 停止） |
|---|---|---|
| 站内（`inbox`） | `notify_inbox_on_start`（默认 false） | `notify_inbox_on_end`（默认 true） |
| 站外（`push`） | `notify_push_on_start`（默认 false） | `notify_push_on_end`（默认 true） |

时机仍是**两档**：`start`（运行开始）与 `end`（终态，success / cancelled / failure 全部归 end），
不引入「仅失败通知」这种第五种状态；矩阵形状固定为 2×2。

### E3. 语义与实现

- 解析集中在一处：`app/models/workflow/notify_flags.py`
  `NotifyChannelFlags.from_model(workflow).channels(is_start=...) -> frozenset[NotifyChannel]`；
- `_notify_run`（`app/services/execution/workflow/notify.py`）按集合决定投递哪些通道，
  集合为空直接返回；调用方（`run_workflow` 开始 / 前置失败兜底、`run_event_handlers` 终态）
  不再各自 `getattr(workflow, "notify_on_*")` 判断，避免口径分叉；
- `WorkflowRunRecord.notified` 语义不变：仍只表示**站外推送**已发出；只命中站内通道时不置位
  （站内幂等由 be-message 按 `(target_value, title)` 兜底；标题已带 `#run_id[:8]` 后缀）。

### E4. 兼容性

- 旧字段 `notify_on_start` / `notify_on_end` **保留**（DB 列不删，管理端 / 导出 JSON / 旧客户端仍可读），
  API 入参仍接受但标记废弃，语义变为「按双通道展开」，且只在对应新字段**未显式给出**时生效
  （用 pydantic `model_fields_set` 判定，避免把「默认值」误当用户意图）；
- 写入时旧列保持为派生值：`notify_on_start = inbox_on_start or push_on_start`，
  `notify_on_end = inbox_on_end or push_on_end`，旧读方不会看到「全关」；
- 迁移 `20261031_wf_notify_channels`：新增 4 列（先带 server_default 保证 NOT NULL 可加，
  再按旧列 copy 到两个通道，最后去掉 server_default）；存量工作流升级后行为与升级前一致。

### E5. 前端

见 `docs/frontend_requirements/工作流运行通知通道开关.md`：`WorkflowEditDialog` 的「运行通知」区
改为 2×2 勾选矩阵（行 = 站内 / 站外，列 = 开始 / 结束），保存提交 4 个布尔字段。

## 自检清单

- [ ] `actions/**` 内不出现站点名 / 域名 / 选择器 / 业务资源类型；
- [ ] 通知失败绝不影响工作流执行，且必须有 warning 日志；
- [ ] 去重生效：同一 key 同一天只发一次（单测覆盖）；
- [ ] `WorkflowRunSummary` 新字段有默认值，旧数据可读；
- [ ] 熔断文案含步骤级（成功/总数）与循环级（轮次 + 体内成败）上下文，口径不混淆；
- [ ] 单测：容忍失败统计、告警文案渲染、notify 通道/去重/失败降级、
      循环聚合（轮次/体内动作、同名多次实例化合并）；
- [ ] 运行通知 4 个开关（站内/站外 × 开始/结束）各自独立生效，只开一端时不走另一通道；
      旧客户端只传 `notify_on_start` / `notify_on_end` 时按双通道展开；
- [ ] 动作 JSON 与数据库 `steps` 一致（源动作 + Fork）。
