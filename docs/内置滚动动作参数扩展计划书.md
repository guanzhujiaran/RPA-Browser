# 内置滚动动作参数扩展计划书（scroll x / y）

## 背景

`scroll` 动作目前只有两种语义（`app/services/execution/actions/interaction.py`）：

- 提供 `selector` → `locator.scroll_into_view_if_needed()`：把**某个元素**滚进视野；
- 不提供 `selector` → `window.scrollTo(0, 0)`：滚回**页面顶部**。

没有「按方向/像素滚动页面」的能力。实际场景里经常需要「像人一样往下滚一屏」，例如：

- `参与B站抽奖` 需要先往下滚到评论区才会触发 B 站动态页的评论区懒加载；
- 无限滚动列表需要逐步滚动触发加载。

用 `scrollIntoView` 近似代替的问题：目标元素必须已经在 DOM 里，否则 `locator` 会先隐式等待再超时失败，实际上**一点都没滚**；而且一次滚动整段距离，和真人逐步滚动差别大，更容易被风控识别。

## 设计

### 1. 参数（`ScrollParams`）

在保持兼容的前提下新增 4 个参数：

| 参数 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `x` | `int \| None` | `None` | 水平滚动像素，正数向右 |
| `y` | `int \| None` | `None` | 垂直滚动像素，正数向下 |
| `steps` | `int` | `1` | 分几步滚完（=1 表示一次滚到位） |
| `interval_ms` | `int` | `200` | 每步间隔（毫秒） |

`x` / `y` 任一非 `None` 即进入**滚轮模式**，此时忽略 `selector`。

### 2. 执行优先级（`ScrollAction._execute`）

1. `x` 或 `y` 非空 → 分 `steps` 次调用 `page.mouse.wheel(dx, dy)`，每次间隔 `interval_ms`；
2. 否则有 `selector` → `locator.scroll_into_view_if_needed()`（行为不变）；
3. 否则 → `window.scrollTo(0, 0)`（行为不变，滚回顶部）。

为什么用 `page.mouse.wheel` 而不是 `window.scrollBy`：

- 它是浏览器原生输入事件，会正常触发 `IntersectionObserver` / `scroll` 监听，懒加载才会真正被唤醒；
- 不依赖任何站点选择器，属于与业务无关的通用机制；
- `steps` + `interval_ms` 让滚动节奏接近真人，降低风控特征。

### 3. 兼容性

- 存量动作 JSON 只用到「selector 模式」，参数默认值不变，行为完全不变；
- `ScrollResult` 不变（仍为 `scrolled: bool`）；
- 前端动参表单按 `params` 模型自动渲染，新增参数可选填。

### 4. 使用方（`参与B站抽奖` 动作）

「加载评论区」循环里的滚动步骤从

```json
{ "action_id": "scroll", "params": { "selector": "bili-comments", "timeout": 5000 } }
```

改为

```json
{ "action_id": "scroll", "params": { "x": 0, "y": 900, "steps": 3, "interval_ms": 250 } }
```

（滚轮向下 900px，分 3 步；随后仍由 `wait bili-comment-thread-renderer` + `comments_ready` 的
`break_condition` 决定是否停止重试。）

## 校验与测试

1. **单测（离线，不依赖真实浏览器）**：用伪造 page 对象断言
   - 有 `x`/`y` → 调用 `mouse.wheel`，次数 = `steps`，累计位移 = `y`；
   - 无 `x`/`y` 且有 `selector` → 调用 `scroll_into_view_if_needed`，不调用 `wheel`；
   - 都不给 → 调用 `window.scrollTo(0, 0)`；
   - 参数校验：`steps` / `interval_ms` 越界报错。
2. **静态校验**：`workflow_step_adapter.validate_python` + `PipelineBuilder.build` 编译通过。
3. **落库**：更新 `compositeactionmodel.steps`（源动作 + Fork），回读与 JSON 一致。
4. **实跑**：在 RPA-Browser 里跑一次相关工作流，确认评论区加载率提升、
   `抄评论失败` 次数下降。
