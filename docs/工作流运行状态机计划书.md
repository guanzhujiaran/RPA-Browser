# 工作流运行状态机计划书

> 状态：已实现（第一步：状态机 + 单一写入口）
> 关联代码：`app/services/execution/run_state_machine.py`（新增）、
> `app/services/execution/crud_service/workflow_run_crud.py`、
> `app/services/membership/membership_service.py`

## 1. 背景

一次工作流运行的状态原先由 **6 处代码各自写入**，每条路径自己判断「能不能改」，
漏判就会写出脏状态（取消后又变 running、成功被覆盖成失败）：

| 写入点 | 原实现 |
|---|---|
| 创建排队记录 | `create_queued(status=QUEUED)` |
| 创建直接运行记录 | `create_running(status=RUNNING)` |
| 排队 → 运行 | `mark_running`：`model.status = RUNNING` |
| 排队取消 / 超时 | `finish_queued`：`model.status = status` |
| 正常收口 | `finish`：`UPDATE ... WHERE status='RUNNING'`（CAS） |
| 僵尸收口 | `interrupt_stale_running` / `_force_interrupt_run`：批量 `UPDATE` + 行锁逐条 |
| 计费熔断 / 会话丢失 | `membership_service` 里直接 `current.status = FAILED` + 裸 `UPDATE` |

由此产生的补偿机制（30s 停止宽限期、宽限扫描、僵尸运行扫描、启动恢复）本质都是
「没有单写入口」的补丁。另外停接口此前还另写了一份收尾（已在
`docs/工作流停止计划书.md` §3.4 收敛到 `finalize_run_after_task`）。

## 2. 目标与非目标

**目标**
- 状态迁移规则**只有一份**（迁移表 + 校验函数）；
- 状态落库**只有一处**（`WorkflowRunCrudService`），业务侧不再直接赋值；
- 非法迁移立刻报错（而不是写出脏状态后被下游逻辑猜）；
- 幂等：重复收口 / 重复停止不应因为「终态 → 终态」而报错。

**非目标（本轮不做）**
- 不做事件溯源（event sourcing），DB 仍是唯一真相；
- 不引入进程内事件总线 / MQ 派发副作用（SSE、通知、计费仍按现有路径调用）；
- 不改状态枚举、不加 `STOPPING` 中间态。

## 3. 设计

### 3.1 纯规则模块

`app/services/execution/run_state_machine.py`（不碰数据库、无副作用）：

```python
ALLOWED_TRANSITIONS = {
    QUEUED:      {RUNNING, CANCELLED, FAILED, INTERRUPTED},
    RUNNING:     {SUCCESS, FAILED, INTERRUPTED, CANCELLED},
    SUCCESS:     set(),
    FAILED:      set(),
    INTERRUPTED: set(),
    CANCELLED:   set(),
}
```

- `ensure_transition(current, target, run_id=...)`：非法抛 `WorkflowRunStateError`，
  同状态视为幂等直接放行；
- `ensure_initial_status(status)`：只允许 `queued` / `running` 作为初始状态；
- `is_terminal` / `allowed_targets` / `can_transition` / `normalize_status` 供查询与日志。

为什么放在 `app/services/execution/` 而不是 `execution/workflow/`：`workflow` 子包的
`__init__` 会 re-export `launcher` → `run_workflow` → `crud_service`，而 crud 又要用
状态机，放在子包里会形成循环导入。

### 3.2 单一写入口

状态只在 `WorkflowRunCrudService` 里落库，且每次写前过状态机：

| 方法 | 校验 |
|---|---|
| `create_queued` / `create_running` | `ensure_initial_status(...)` |
| `mark_running` | `ensure_transition(model.status, RUNNING)` |
| `finish_queued` | `ensure_transition(model.status, status)` |
| `finish` | `ensure_transition(RUNNING, status)`（SQL 侧仍有 `WHERE status='RUNNING'` 做 CAS） |
| `interrupt_stale_running` / `_force_interrupt_run` | `ensure_transition(RUNNING, INTERRUPTED)` |

`membership_service` 的两处写（崩溃兜底 `current.status = FAILED`、余额耗尽熔断的
裸 `UPDATE`）改为先 `ensure_transition(current.status, FAILED, run_id=...)`。

### 3.3 为什么保留 SQL CAS

状态机的校验发生在**内存态**；真正的互斥仍靠 `UPDATE ... WHERE status='RUNNING'`
（与僵尸收口并发时只有一个能命中）。两者分工：状态机防「代码写错」，CAS 防「并发覆盖」。

## 4. 影响面

- 行为不变：所有现存路径的迁移都在迁移表内（已逐一核对 6 处写入点）；
- 新增失败面：若将来有人写 `finish(SUCCESS)` 后又想把记录改回 `RUNNING`，现在会抛
  `WorkflowRunStateError`（这正是目的）；
- 无数据库结构变更、无需迁移脚本；
- 无对外接口签名变更。

## 5. 验证清单

1. `pytest test/execution_engine/test_run_state_machine.py`：迁移表全覆盖（合法 / 非法 / 幂等）；
2. `pytest test/execution_engine/test_run_queue.py`：排队相关回归；
3. 静态：`uv run python -m compileall app`；导入 `workflow_router` 无循环依赖；
4. 实跑：
   - 手动运行成功 → `success`；失败 → `failed`；
   - 运行中停止 → `cancelled`（重复停止仍幂等返回）；
   - 排队中停止 → `cancelled`，且不会被重新拉成 `running`；
   - 运行中 kill -9 重启 → `interrupted`，可断点恢复；
   - 余额耗尽熔断 → `failed`。

## 6. 第二步：运行状态事件（已实现）

### 6.1 总线

`app/services/execution/run_events.py`：

- `WorkflowRunStatusChanged`（pydantic）：`run_id / from_status / to_status / reason / occurred_at`；
  `from_status = None` 表示新建记录；
- `WorkflowRunEventBus`：同步发布，同步订阅者当场执行，协程订阅者 `create_task` 丢回循环；
  **单个订阅者抛错只告警**，不影响其它订阅者、更不影响状态落库；
- `publish_status_changed(...)`：唯一发布入口，内部吞掉所有异常（事件是旁路）。

发布点全部在 **DB 提交之后**：

| 位置 | 事件 |
|---|---|
| `create_queued` / `create_running` | `None → QUEUED / RUNNING` |
| `mark_running` | `QUEUED → RUNNING` |
| `finish_queued` | `QUEUED → 终态` |
| `finish` | `RUNNING → 终态`（仅 CAS 命中时发，幂等空操作不发） |
| `interrupt_stale_running` / `_force_interrupt_run` | `RUNNING → INTERRUPTED` |
| `membership` 崩溃兜底 / 余额熔断 | `RUNNING → FAILED` |

### 6.2 默认订阅者

`app/services/execution/run_event_handlers.py`，启动时由 `app/setup.py` 注册
（必须在启动期 `interrupt_stale_running` 之前，否则启动收口的事件没人消费）：

| 订阅者 | 作用 |
|---|---|
| `log_run_status_changed` | 结构化审计日志：`run=xxx running → cancelled, reason=...` |
| `sync_workflow_last_run` | 终态时刷新工作流卡片快照 `last_run_status / last_run_at` |
| `settle_run_billing` | 终态且带摘要时结算时长 + 使用统计（仅定时任务扣费，幂等） |
| `notify_run_finished` | 终态且带摘要时发送结束通知（成功/取消/失败，受 `notify_on_end` 约束） |

配套：`run_workflow` 里原先直接写 `update_run_state(status=...)` 的两处（正常收口、
前置校验失败）已删除，改由 `sync_workflow_last_run` 统一维护，避免两处口径。

### 6.3 SSE 暂不搬

SSE 进度帧是延迟敏感路径（步骤级事件由 `progress_reporter` 直接推送），且依赖
上报器实例与连接状态，不适合走「状态事件 + 异步订阅」；终态帧仍由执行体在
`finish()` 之后直接 `flush`。状态事件只负责**可延后、可失败**的副作用。

### 6.5 事件摘要（`WorkflowRunSummary`）与通知 / 计费迁移

为什么要有摘要：通知正文需要步骤数 / 耗时 / 失败原因，计费需要「拿到会话后开始计时」
的可计费时长——这些只能在执行体里算。把它们做成事件契约，订阅者就不必回头读执行期对象。

```python
class WorkflowRunSummary(SQLModel):
    total: int = 0
    success_count: int = 0
    failed_count: int = 0
    duration_ms: float = 0.0
    billable_seconds: float = 0.0     # 会话获取 → 运行结束
    error_message: str | None = None
```

- `finish(..., summary=run_summary)` 把它挂到终态事件上；非终态事件 `summary=None`；
- `settle_run_billing`：调用 `MembershipService.settle_workflow_run(...)`，`is_scheduled`
  取自运行记录的 `trigger_source`；该函数本身幂等（`settled_seconds` 非空即跳过）且内部吞异常；
- `notify_run_finished`：先看 `record.notified` 去重，再按 `notify_on_end` 决定是否推送，
  推送成功后 `mark_notified`；
- 执行体中原先的「结算 + 结束通知 + mark_notified」三段代码已删除，只保留
  「开始通知」（`notify_on_start`）与前置校验失败的兜底通知（那时还没有运行摘要）。

顺序变化说明：结算从 `finish()` **之前**移到终态事件之后（即 `finish()` 提交之后）。
`settle_workflow_run` 只操作 `settled_seconds` 与账户余额、不依赖运行状态，幂等性由
`settled_seconds` 保证，因此顺序调整不影响金额。

### 6.4 明确的边界

- DB 是唯一真相：事件丢失只影响派生态，不影响运行记录；
- 订阅者必须幂等（同一条终态事件可能重复到达：幂等收口 / 兜底路径）；
- 多实例时把总线换成 DB outbox / Redis，订阅者代码不变；
- 测试：`test/execution_engine/test_run_events.py`（分发 / 异步 / 异常隔离 / 重名覆盖 /
  无循环丢弃 / 摘要透传）。
