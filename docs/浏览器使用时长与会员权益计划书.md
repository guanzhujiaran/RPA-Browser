# RPA 浏览器使用时长与会员权益计划书（v1）

> 状态：已确认方案（2026-10-02），本计划书为后续改动的唯一依据。

## 1. 需求概述

为 RPA 浏览器增加「使用时长」体系：

1. **用户时长统计**：按用户 / 浏览器 / 日期统计浏览器使用时长（含工作流消耗时长），可查询流水与日统计。
2. **时长获取途径**：签到、参与活动（后台/运营发放）、兑换码兑换（本期不接第三方支付，支付订单仅预留设计）。
3. **会员卡**：
   - **月卡**：有效期内运行定时工作流**不扣时长**；
   - **时长卡**：一次性时长包，用完为止。
4. **消耗规则**：**只有定时任务（`trigger_source=schedule`）的工作流运行消耗时长**；手动启动浏览器调试、手动运行工作流一律不消耗。
5. **计费粒度**：按会话时长 —— 定时工作流启动前校验余额，运行结束后按实际运行时长（向上取整到分钟）扣减。

## 2. 数据模型（`app/models/database/membership/models.py`）

所有表继承 `BaseSQLModel`（统一 created_at / updated_at），mid 一律 BIGINT 存储、对外传 str。

| 表 | 说明 |
|---|---|
| `userdurationaccount` | 用户时长账户：`mid`(唯一)、`balance_seconds`、`total_granted_seconds`、`total_consumed_seconds` |
| `durationledger` | 时长变动流水：`mid`、`change_seconds`(±)、`balance_after`、`change_type`(SIGN_IN/ACTIVITY/REDEEM/CONSUME/ADJUST)、`workflow_id`、`run_id`、`browser_id`、`remark` |
| `monthcardrecord` | 月卡记录：`mid`、`source`(REDEEM/ACTIVITY/ADMIN)、`start_at`、`expire_at`、`remark`；有效判定 `now ∈ [start_at, expire_at)` |

> 月卡时长换算约定：**不使用日历月**，一律按「天 × 24 小时」顺延（`timedelta(days=N)`），
> 「一个月」即生成兑换码时取 `card_days=31`；已有生效月卡时新卡自当前最晚到期时间起顺延。
| `signinrecord` | 签到记录：`mid` + `sign_date`(date) 唯一；`reward_seconds`、`continuous_days` |
| `redemptioncode` | 兑换码：`code`(唯一)、`code_type`(DURATION/MONTH_CARD)、`duration_seconds`、`card_days`、`max_uses`、`used_count`、`is_enabled`、`expire_at`、`batch_no`、`remark` |
| `coderedemptionrecord` | 兑换流水：`code`、`mid`、`redeemed_at`；(code, mid) 唯一防止重复兑换 |
| `browserusagedailystat` | 使用日统计：`mid`、`stat_date`、`browser_id`、`workflow_seconds`、`manual_seconds`、`workflow_run_count`；(mid, stat_date, browser_id) 唯一 |

## 3. 业务规则

### 3.1 消耗（`MembershipService`）

1. 定时工作流（SCHEDULE）启动前：`check_run_allowed(mid)`：
   - 存在有效月卡 → 放行；
   - 否则 `balance_seconds > 0` → 放行（余额不足按分钟粒度扣减，允许欠最多 1 分钟的尾差）；
   - 余额 <= 0 → 拒绝运行，记录运行失败（`DURATION_INSUFFICIENT`），发失败通知。
2. 运行结束：`consume(mid, seconds=ceil(run_seconds/60)*60)`：
   - 有效月卡 → 不扣，仅记统计；
   - 事务内行锁（`WITH FOR UPDATE`）扣减 `balance_seconds`，写 CONSUME 流水 + 日统计 `workflow_seconds`。
3. 手动运行 / 手动调试：不扣时长；统计侧仍记录 `manual_seconds`（不收费的统计口径）。

### 3.2 获取

| 途径 | 规则 |
|---|---|
| 签到 | 每自然日 1 次；固定 60 分钟 + 累计签到命中 7/14/28 天里程碑时额外叠加（详见 §12.1，v1.4 起口径变更） |
| 兑换码 | DURATION → 直加余额；MONTH_CARD → 自领取日起 +`card_days` 天（可与已有月卡顺延）；每人每码限兑 1 次，受 `max_uses` / `expire_at` / `is_enabled` 约束 |
| 活动 / 后台调整 | 管理侧直接调 `grant()`，写 ACTIVITY / ADJUST 流水（本期提供 service 能力，管理界面后置） |

支付：本期不接第三方支付；支付入账设计见 §3.3。

### 3.3 支付入账设计（Casdoor 收银台，服务端校验，方案A：商品名约定）

安全原则：**入账只认「RPA 后端服务端到服务端」从 Casdoor 查到的支付真实状态**；前端跳转参数（`transactionOwner/transactionName`）仅作为触发线索，不作为入账依据。

Casdoor 事实（依据其文档）：
- 商品配置 `Success URL` 后，支付完成时 Casdoor 以 `?transactionOwner={paymentOwner}&transactionName={paymentName}` 跳转该 URL；
- **配置 Success URL 后 Casdoor 不再自动完成交易，必须由跳转目标调用 `api/notify-payment/{owner}/{name}` 完成交易**，否则支付失败。

#### 商品命名约定（唯一配置点 = Casdoor 后台）

商品 `name` 按以下约定命名，后端入账时解析（大小写不敏感，模式可出现在名称任意位置）：

| 名称包含 | 权益 | 示例 |
|---|---|---|
| `duration-<N>m` | 时长 N 分钟 | `rpa-duration-30m` |
| `duration-<N>h` | 时长 N 小时 | `rpa-duration-2h` |
| `monthcard-<N>d` | 月卡 N 天（一个月=31天） | `rpa-monthcard-31d` |

无法解析的商品支付到账后**拒入账并打 warning 日志**（钱不丢，Casdoor 侧支付已完成，修名/补机制后可经兜底对账补入账）。

#### 流程

1. 商品在 Casdoor 后台创建（按约定命名 + 价格/支付 Provider/`successUrl` 指向前端 `/app/rpa-browser/membership`）——**无需任何 RPA 侧配置**；
2. 用户点击购买 → 前端跳 Casdoor 收银台 `/buy/<product_name>` 完成支付；
3. Casdoor 跳回前端，query 带 `transactionOwner` / `transactionName` → 前端调 `POST /payment/notify` 转交；
4. RPA 后端调 Casdoor `notify-payment` 完成交易 → `get-payment` 服务端核验 `Paid` + 支付归属 → 解析商品名 → 幂等入账（`paymentorder` 唯一键 = payment name）；
5. `POST /payment/confirm` 兜底对账保留；商品列表接口改为实时从 Casdoor `get-products` 拉取（解析出规格的商品才展示）。

要点：
- 防伪造：入账以服务端 `get-payment` 的 `Paid` + 归属校验为准；
- 幂等：`paymentorder.payment_name` 唯一约束 + 先查后插；
- 已废弃：`paymentproduct` 映射表与管理端映射接口（表若已建则留存不碍事，代码不再读写）。

## 8. 修订（v1.1，长任务 / 崩溃安全）

v1 的「运行结束后一次性结算」存在漏洞，v1.1 修订如下：

1. **心跳预扣（防长任务白嫖）**：后台 APScheduler 任务（间隔 `workflow_billing_heartbeat_interval`，默认 300s）扫描 `WorkflowRunRecord` 中 `status=RUNNING` 且 `trigger_source=SCHEDULE` 的运行：
   - 无月卡且余额 > 0：**按差额预扣**到当前墙钟分钟的目标额度（写 CONSUME 流水；详见 §14.2），同一时刻重复执行扣 0，支持多实例幂等；
   - 无月卡且余额 <= 0：**熔断** —— 强制 `release_browser_session` 关闭会话、运行记录标记失败；执行线程随后自然失败退出；
   - 月卡生效中：跳过。
   长任务最多「偷跑」不足一个心跳周期。
2. **崩溃兜底结算**：扫描发现 RUNNING 但 `live_service` 中已无对应会话（进程重启 / 会话丢失）→ 按 `now - started_at` 整分钟兜底扣减（受余额封顶）、标记 `settled_seconds`、运行记录置失败。
3. **最终结算幂等**：`WorkflowRunRecord.settled_seconds`（None=未结算）。最终结算 = `目标(向上取整分钟) - 已预扣`，差额补扣（不为负、不冲正；心跳竞态导致的少量多扣接受）。已结算的运行不重复结算。
4. **账户并发创建兜底**：`get_or_create_account` 撞唯一约束时重读。
5. 手动调试时长埋点（`manual_seconds`）暂不实施，字段保留，口径见前端需求文档。
6. **并发安全（§8 补充）**：
   - 账户余额：所有扣减路径 `SELECT ... FOR UPDATE` 行锁账户行，多浏览器并发串行扣减、不为负；
   - 心跳 vs 最终结算：统一「先锁 run 行（FOR UPDATE）再锁账户行」的加锁顺序，消除竞态双扣与锁序死锁；
   - 同一浏览器并发定时工作流：runner 会话获取后检查 `entry.workflow_run_id` 已被占用则拒绝执行（一次只允许一个工作流占用一个浏览器会话），避免双份计费/统计与熔断误伤；该检查为**进程内**互斥，多实例部署由前置校验「同一 `browser_id` 存在 RUNNING 运行记录则拒绝」兜底（见 §14.4）；
   - 日统计同行并发（同浏览器同日心跳/结算碰撞）已改为 SQL 层原子自增（`SET x = x + ?`），不再丢失更新（原为读改写无锁，见 §14.4）；
   - 定时工作流启动校验（余额>0）与首次预扣之间为 TOCTOU：多浏览器同时启动可短暂超卖到首个心跳周期，由预扣/熔断收敛，接受。

## 10. 修订（v1.2，时长明细「获得 + 消耗」一起展示）

背景：用户侧只看到「用掉的时长」，看不到时长的来源（签到 / 兑换 / 活动 / 购买）明细。
实际 `durationledger` 早已把获得与消耗记在同一张表（`change_seconds` 正负区分），
但查询接口不支持按类型过滤，前端只能在已加载的分页内做展示层过滤，无法翻到全部历史获得记录。
故本次把过滤下沉到服务端：

1. **`/ledger_list` 请求体新增可选字段 `change_types`**（`LedgerListRequest`，继承 `BasePaginationReq`）：
   - 不传 / 空串 → 不过滤（保持原有行为，向后兼容）；
   - 逗号分隔的多个 `LedgerChangeType` 合法值（如 `sign_in,redeem`）→ `IN` 过滤；
   - 每一项取值直接用枚举声明，非法值由 pydantic 校验拦截（422），不新增业务码。
2. **「仅获得 / 仅消耗」的语义归一**：写库侧保证除 `CONSUME`（心跳预扣 / 最终结算，统一负数）外
   其余类型均为正数（`ADJUST` 人为填正数）。因此前端筛选口径为：
   - 全部 → `change_types` 留空；
   - 仅消耗 → `change_types=consume`；
   - 仅获得 → `change_types=sign_in,activity,redeem,adjust`。
3. **`MembershipService.list_ledger` 增加 `change_types` 关键字参数**（默认 `None`），作用于
   `where` 条件与 `count`，`total` 随之收敛为过滤后的条数，分页语义与之前一致。
4. **数据库**：无表结构变化，不需要新迁移。
5. **前端**：见 `Vue3FrontEndDemoExercise/docs/frontend_requirements/rpa_browser_membership.md` §5；
   本次接口变更需**重新生成 `hey-api` SDK**，由用户手动执行后再接入前端筛选。

## 11. 修订（v1.3，签到日历）

背景：用户只能从流水中看到「某天签到 +30 分钟」，看不到本月签了几天、每天各自奖励多少，
也无法直观感知「连续签到越久每天奖励递增（30 分钟 +10 分钟/天，单日封顶 60 分钟）」这一规则。
故新增按月的签到日历查询接口，数据全部落在既有 `signinrecord` 表上（无表结构变化）。

1. **新增用户侧接口 `POST /browser/membership/sign_in_calendar`**：
   - 请求 `SignInCalendarRequest`：`month: str | None`，格式 `YYYY-MM`，不传取当前月；
     格式非法由 pydantic 校验拦截（422），不新增业务码；
   - 响应 `SignInCalendarResponse`（数值字段一律 str）：
     | 字段 | 含义 |
     |---|---|
     | `month` | 实际查询的月份 `YYYY-MM` |
     | `days` | 当月 1 号至月末逐日条目，**按自然日补齐**（未签到 `signed=false`、`reward_seconds=0`），前端直接渲染日历无需再拼装 |
     | `signed_days` | 当月已签到天数 |
     | `total_reward_seconds` | 当月签到合计奖励秒数 |
     | `current_continuous_days` | 最新一条签到记录的连续天数（无签到记录为 0） |
   - 单日条目 `SignInCalendarDay`：`date`（`YYYY-MM-DD`）、`signed`、`reward_seconds`、`continuous_days`。
2. **服务层**：`MembershipService.list_sign_in_records(mid, session, month)` 返回该月 `SignInRecord`
   列表（按日期升序）；日期补齐与合计等聚合在控制器组装，保持服务层只做数据访问。
3. **奖励口径**：日历上展示的 `reward_seconds` 直接取 `signinrecord.reward_seconds` 快照，
   与当日实际入账（`durationledger` 的 `SIGN_IN` 流水）一致；连续签到的递增由既有
   `sign_in` 逻辑（`SIGN_IN_BASE/SIGN_IN_CONTINUOUS_BONUS/SIGN_IN_DAILY_CAP`）保证，日历不做二次计算。
4. **数据库**：无表结构变化，不需要新迁移。
5. **前端**：见 `Vue3FrontEndDemoExercise/docs/frontend_requirements/rpa_browser_membership.md` §6；
   本次为新增接口，需**重新生成 `hey-api` SDK**，由用户手动执行后再接入日历。

## 12. 修订（v1.4，签到玩法改版：固定时长 + 里程碑奖励 + 补登卡 + 档位兑换）

背景：v1.2/v1.3 的签到是「连续递增 +10 分钟/天、单日封顶 60 分钟」，用户实际反馈：

1. 连续天数口径不友好（断签即回到起点，且要记住"连续 N 天"），改为**累计签到天数**视角；
2. 奖励规则简化为**每天固定时长**，额外奖励只挂在**累计里程碑**上（7 / 14 / 28 天）；
3. 增加**补登卡**道具：可补签当月漏掉的日期，补签消耗卡片；
4. 增加**奖励档位兑换**（入门 / 进阶 / 巅峰）：累计签到到达 7 / 14 / 28 天各解锁一档，
   用户主动点「兑换」获得奖励。奖励项**只使用本项目已有的资产（时长 + 补登卡）**，
   不引入积分 / 能量 / 抽奖次数等不存在的资产。

### 12.1 奖励口径（重写 `sign_in`）

```
每日签到奖励 = SIGN_IN_DAILY_REWARD_SECONDS（固定 60 分钟）
             + 累计签到天数命中里程碑时的额外奖励（叠加）
```

- 里程碑（累计签到天数，`total_sign_days` 命中即得，可叠加）：

| 累计签到天数 | 里程碑 | 额外奖励 |
|---|---|---|
| 7 | `SIGN_REWARD_MILESTONES[0]` | +60 分钟 |
| 14 | `SIGN_REWARD_MILESTONES[1]` | +120 分钟 |
| 28 | `SIGN_REWARD_MILESTONES[2]` | +240 分钟 |

- 里程碑奖励**每档仅发放一次**（由 `sign_reward_exchange` 无关、由「当日累计天数是否命中里程碑」判定；
  同一里程碑在后续签到日不再重复发放，靠累计天数单调递增天然保证）。
- **存量数据**：v1.3 及之前的 `signinrecord.reward_seconds`（按连续递增发放）**不回溯重算**，
  新规则只对上线后的新签到 / 补签生效；`continuous_days` 字段保留只读（历史快照），
  新逻辑不再依赖它，累计天数改由 `usersignprofile.total_sign_days` 维护。
- 移除 `SIGN_IN_CONTINUOUS_BONUS_SECONDS` / `SIGN_IN_DAILY_CAP_SECONDS` 常量。

### 12.2 数据库变更（Alembic 新增手写 revision）

1. **新表 `usersignprofile`**（用户签到档案，`mid` 唯一）：
   - `mid` BIGINT、`total_sign_days` INT（累计签到天数，含补签）、
     `makeup_cards` INT（持有补登卡数量，默认 0）、`created_at` / `updated_at`。
2. **新表 `signrewardexchange`**（档位兑换记录，`(mid, tier)` 唯一保证每档一次）：
   - `mid` BIGINT、`tier` VARCHAR（`basic` / `advanced` / `peak`）、
     `reward_seconds` INT（发放时长快照）、`makeup_cards` INT（发放补登卡快照）、
     `total_sign_days` INT（兑换时的累计天数快照）、时间戳。
3. **表 `signinrecord` 增列**：
   - `is_makeup` BOOLEAN NOT NULL DEFAULT 0（是否补签产生）、
   - `makeup_card_cost` INT NOT NULL DEFAULT 0（本次消耗的补登卡数，正常签到为 0）。
4. `scripts/initd/init_database.py` 同步导入新模型，保持一键建库可用。

### 12.3 补签规则

- 入口：日历中当月**已漏签的过去日期**（「未打卡（可补登）」格）。
- 限制：
  - 目标日期必须落在**当前自然月**且**早于今天**；
  - 目标日期**未签到**（正常签到或已补签都不行）；
  - 每次补签消耗 **1 张补登卡**，卡数不足直接拒绝；
  - 每天可多次补签不同日期（不限制当日补签次数），单日重复补同一日期幂等拒绝。
- 奖励：按 §12.1 口径发放（基础固定时长 + 里程碑额外，若命中），
  补签同样计入累计签到天数，并写入 `durationledger`（`change_type=SIGN_IN`，备注标注「补签」）。
- 记录：`signinrecord` 落一行 `is_makeup=1`、`makeup_card_cost=1`。

### 12.4 奖励档位与补登卡来源

- 档位定义（常量 `SIGN_REWARD_TIERS`，解锁门槛为累计签到天数）：

| 档位 | tier | 解锁门槛 | 发放时长 | 发放补登卡 |
|---|---|---|---|---|
| 入门档 | `basic` | 累计 7 天 | 60 分钟 | 1 张 |
| 进阶档 | `advanced` | 累计 14 天 | 180 分钟 | 2 张 |
| 巅峰档 | `peak` | 累计 28 天 | 480 分钟 | 3 张 |

  时长写 `durationledger`（`change_type=ACTIVITY`，备注「签到奖励兑换：<档位名>」）。
- 补登卡的**唯一来源**即档位兑换（管理端手动发放本期不做，字段与流水已就绪，后续可追加）。

## 13. 修订（v1.5，奖励配置外置 JSON + 概览接口对齐）

**JSON 文件**（与 `app/data/permissions.json` 同一套模式，docker volume 挂载持久化），

### 13.1 配置文件

- 路径：`RPA-Browser/app/data/sign_in_rewards.json`（容器内 `/app/app/data/sign_in_rewards.json`）。

  （`./RPA-Browser/app/data:/app/app/data` 已覆盖目录，这里再补一条文件级挂载保证容器重建不丢）。
- 结构（**只含本项目真实存在的资产：时长 + 补登卡**）：

  "makeup_card_max": 4,

## 14. 修订（v1.6，一轮全面 Code Review 后的健壮性收敛）

本次为 bug 修复与口径收敛（无新功能、无新 DB 迁移），按 review 结论统一以下口径。

### 14.1 计费口径修正（手动运行不再扣费）

- §3.1 约定「只有定时任务消耗时长」，但 `settle_workflow_run` 原实现无条件调用 `finalize_run`，
  导致**手动调试 / 手动运行虽不校验余额却照扣时长** —— 与开局校验口径矛盾。
- 修正：`settle_workflow_run` 仅在 `is_scheduled=True` 时结算扣费；手动运行照常记
  `workflow_seconds` / `manual_seconds` 使用统计，不计 `workflow_run_count`。

### 14.2 心跳预扣改为「差额式幂等」（替代原「固定扣一个间隔」）

- 原实现每轮心跳都固定扣 `workflow_billing_heartbeat_interval`，存在两类错误：
  1. 多实例部署时每个进程都注册同一个 interval job → 同一 run 每轮被扣 N 倍，且 §8.3
     明确「不冲正」，多扣无法自动纠正；
  2. 只跑了几十秒的任务刚被扫到就扣掉整个周期（默认 300s）。
- 修正（§8.1 同步更新）：心跳按 **目标额度差额** 补齐 —— `已扣 = Σ CONSUME 流水`，
  `本次扣 = ceil((now - started_at)/60)*60 - 已扣`（>0 才扣）。同一墙钟时刻重复执行结果为 0，
  天然支持多实例与短任务。
- 配套：`scheduler` 注册加 `max_instances=1` + `coalesce=True`（单进程内不叠跑）；
  心跳扫描下推 `settled_seconds IS NULL` 并加 `_HEARTBEAT_BATCH` 上限。

### 14.3 时区统一：自然日判定必须以业务时区为准

- 新增 `app/utils/time_util.py`（`now_local()` / `today_local()`），返回 **naive datetime**
  （保持与库表 naive DATETIME 可比），时区优先级：签到 JSON 配置 `timezone`
  > `settings.app_timezone`（新增，默认 `Asia/Shanghai`）> 内置兜底。
- 签到时间 Ray(total)、`stat_date`、日历接口、月卡有效期判定全部改走该工具，替代原先散落的
  `datetime.now()` / `date.today()`，消除容器 TZ=UTC 带来的 8 小时跨日错位与多实例不一致。

### 14.4 并发与事务安全

- **签到档案行锁**：`get_or_create_sign_profile(..., for_update=True)` —— 补登卡扣减、
  累计天数自增、档位封顶发放均为读改写，原实现 1 张卡可并发补签多次。
- **使用统计原子累加**：`record_usage` 改为 SQL 层 `SET x = x + ?`（UPADTE 未命中再 INSERT，
  撞唯一键重试一轮），替换 Python 侧读改写，消除并发下的静默少记。
- **SAVEPOINT 回滚**：所有「懒创建 / 幂等插入」的 `except IntegrityError` 改用
  `session.begin_nested()`，不再整体 `session.rollback()` —— 后者会把调用方已排队的写
  （签到记录、兑换流水）一起丢弃却返回成功。
- **唯一键冲突 → 业务码**：并发重复签到 / 补签 / 档位兑换 / 兑换码重复核销统一转
  `SIGN_IN_ALREADY_TODAY` 等既定业务码，不再冒泡成 HTTP 500。
- **跨进程并发防护**：`entry.workflow_run_id` 是进程内 dict，多实例失效；runner 前置校验
  增加「同一 `browser_id` 存在 RUNNING 运行记录则拒绝」（DB 层兜底，§8.6 同步更新）。

### 14.5 支付安全与健壮性

- `notify_and_grant` 归属校验**前置**：先 `get-payment` 校验属于当前用户，再决定是否
  `notify-payment`。原顺序会允许任意登录用户用 owner/name 让服务端替他推进他人交易。
- `owner` / `name` 字符白名单 `[A-Za-z0-9_-]{1,100}`（路由层）+ Casdoor 客户端侧 URL 段
  `quote(..., safe="")`，双保险防止拼出 `../` 打到 Casdoor 内部其它端点。
- `confirm_payments` 每笔入账包 SAVEPOINT：单笔失败仅记录告警并继续，不再把本轮前面
  已入账的结果整体回滚。
- 商品名解析增加上下限（`_MIN_GRANT_SECONDS` / `_MAX_GRANT_SECONDS` / `_MAX_GRANT_CARD_DAYS`），
  越界的 `duration-0m`、`monthcard-99999d` 等一律拒入账并告警。
- 日志脱敏（`membership_log_mask`），不再明文打印 Casdoor 用户名。

### 14.6 类型与参数约束

- 移除所有 `Dict[str, Any]` / 裸 `dict` 跨层契约：新增 `app/models/membership/dto.py`
  （`StoreProductItem`、`PaymentGrantResult`）与 Casdoor 侧
  `CasdoorPaymentPayload` / `CasdoorProductPayload`（含 camelCase 兼容），符合项目
  「基础类型一律 pydantic」的约定。
- 分页参数兜底 `_normalize_pagination(page, per_page)`：`page >= 1`、
  `1 <= per_page <= 200`，消除负 offset 与响应 `pages` computed_field 除零两类 500。
- 使用统计查询区间校验：日期格式非法 → 业务异常；`end < start` 与跨度
  > `_MAX_USAGE_RANGE_DAYS`（366 天）一律拒绝，查询再加 `limit` 兜底。
- 管理端生成兑换码：数值/日期/枚举统一由 `to_int` / `parse_code_type` / `parse_expire_at`
  转换，越界（`count>500`、`card_days` 越界、负面值）抛 `InvalidMembershipParamException`，
  不再返回裸 ValueError 500。
- 管理端配置接口返回专用 DTO（`SignRewardConfigResponse`），数值以 str 传递，不再直接
  把内部 `SignRewardConfig`（int 字段）泄漏为 API 契约。
- 管理端审计改为复用 `app/services/admin_audit.py:log_admin_action`（独立连接、失败只告警），
  避免审计写入异常连带回滚已生成的兑换码。
