# 同浏览器工作流排队（FIFO 串行）计划书

## 背景

多个工作流可以配置同一个 `browser_id`，但当前同一浏览器**同时只允许一个工作流执行**：

- `_precheck` 查 `workflowrunrecord.status == RUNNING`（`run_workflow.py:79-103`）；
- `run_workflow` 还会检查会话上的 `entry.workflow_run_id`（`run_workflow.py:331-340`）。

后到的运行直接失败：

```
该浏览器已有工作流在执行（run=xxx），请调整调度避免同浏览器并发
```

用户希望：多个工作流共用同一个浏览器，**按提交次序排队执行**；服务重启后，排队的任务重新排队。

## 方案

**内存队列 + DB 排队凭证**（不使用 RabbitMQ）。

- 队列本身是进程内的：`asyncio` FIFO + 事件唤醒，零外部依赖；
- 「排队意图」写入 `workflowrunrecord`：`status = QUEUED`，这是重启后恢复排队的唯一依据；
- 单实例部署（`container_name: fastapi-rpa-browser`，浏览器会话是进程内资源），任务无需跨进程分发，MQ 的削峰/解耦价值用不上，反而要额外维护 ack/重投/顺序。

### 1. 状态机

```
受理 → QUEUED ──(拿到执行权)──→ RUNNING ──→ SUCCESS / FAILED
         │                                   └→ INTERRUPTED（进程重启）
         ├─(用户停止 / 排队超时)──→ CANCELLED / FAILED
```

`WorkflowRunStatusEnum` 新增 `QUEUED = "queued"`。
该列是 MySQL `ENUM`，必须配 alembic 迁移追加枚举值。

### 2. 队列实现（`app/services/execution/workflow/run_queue.py`）

粒度 `(mid, browser_id)`：

| 能力 | 说明 |
|---|---|
| `acquire(key, run_id)` | 入队并**阻塞等待**到队首且无 active；拿到后登记 active |
| `release(key, run_id)` | 释放 active，`set()` 事件唤醒下一个 |
| `position(key, run_id)` | 排队位置（1 基；正在执行时为 0） |
| `cancel(key, run_id)` | 从队列移除（排队中取消），返回是否移除成功 |
| `has_pending(key)` | 该浏览器是否还有排队项（决定是否回收浏览器） |
| 唤醒 | `asyncio.Event`（即时）+ 2s 兜底轮询（防事件丢失） |

队列是**单例内存对象**，进程重启即清空——这正是「重启后重新排队」的来源。

### 3. 执行流程

```
launch_workflow_run
  ├─ 生成 run_id
  ├─ workflow_run_crud_svr.create_queued(...)   # 落库 QUEUED，前端立刻可见
  └─ spawn task → run_workflow
                    ├─ resolve target_browser_id
                    ├─ run_queue.acquire(key, run_id)      # 排队等待
                    ├─ _precheck（含跨进程 RUNNING 兜底）
                    ├─ _open_run：把 QUEUED 记录改为 RUNNING
                    ├─ 执行 steps
                    └─ finally: release + 队列空才回收浏览器
```

- `/workflows/run` **立即返回** `status=queued` + `queue_position`；
- 排队期间不占用会话标记 `entry.workflow_run_id`（调试接口不受排队影响）；
- 排队超时（`workflow_queue_timeout_seconds`，默认 1800s）→ `FAILED`，`error_message=排队超时`。

### 4. 重启恢复

`main.py` lifespan 顺序：

1. `interrupt_stale_running()`：残留 `RUNNING` → `INTERRUPTED`（已有）；
2. `requeue_pending_runs()`（新增）：查 `status=QUEUED` 的记录，按 `id` 升序**重新入队**；
3. `resume_interrupted_runs()`：`resume_on_restart=True` 的从断点续跑（已有，不变）。

语义边界（**不自动重跑被中断的运行**）：

| 重启前 | 重启后 |
|---|---|
| `QUEUED` | 重新排队，保持原顺序 |
| `RUNNING` | `INTERRUPTED`；只有开了 `resume_on_restart` 才断点续跑 |

原因：无去重记录的工作流重跑会重复产生副作用（重复转发/评论），不能默认从头再跑。

### 5. 接口契约

| 接口 | 变更 |
|---|---|
| `POST /workflows/run` | 返回 `status=queued` + `queue_position`（0=正在执行/未排队） |
| `POST /workflows/runs/get` | 响应新增 `queue_position` |
| `POST /workflows/runs` | 列表项新增 `queue_position` |
| `POST /workflows/runs/stop` | 支持取消 `QUEUED` 的运行（出队 + 标 CANCELLED） |

新增字段均有默认值，`operation_id` 不变，前端 SDK 重新生成后向后兼容。

### 6. 浏览器回收

`_release_browser_after_run` 增加条件：**该浏览器队列为空**才回收。
否则 A 结束就关浏览器，B 又要重新拉起（多花 20~40s，还可能丢登录态相关初始化）。

### 7. 多浏览器与并发开关

- `concurrent_exec=true`：每个浏览器各自排队（互不影响）；
- `concurrent_exec=false`：仍按浏览器列表顺序逐个 `await`，每个都先抢自己浏览器的执行权（可能排队等待）。

## 不做的事

- 不引入 RabbitMQ / Redis 作为队列；
- 不做跨进程/多实例的队列协调（单实例部署前提，`_precheck` 的 DB 兜底保留）；
- 不做优先级队列（先到先得；VIP 优先级仅存在于浏览器启动队列）；
- 不自动重跑被中断（`RUNNING`）的运行；
- 不做队列持久化的位置排序字段（重启后按 run 记录 `id` 升序恢复，等价于原提交顺序）。

## 验证

1. 单测 `test/execution_engine/test_run_queue.py`：FIFO 顺序、取消排队、位置计算、释放唤醒、超时出队；
2. 静态校验：`alembic upgrade head` 后 `status` 枚举含 `QUEUED`，`check_schemas` 通过；
3. 实跑（同一浏览器两个工作流）：
   - 先启 A，再启 B → A `RUNNING`、B `QUEUED`（`queue_position=1`）；
   - A 结束 → B 自动转 `RUNNING`，无需人工干预；
   - 排队中调用停止 → B `CANCELLED` 且不再执行；
   - 运行列表 / 运行详情能读到 `queue_position`；
4. 重启重排：A 运行时 kill -9 服务 → 重启后 A 变 `INTERRUPTED`，B 仍是 `QUEUED` 并重新排队（若无 C 则立即执行）；
5. 浏览器回收：A/B 都在队列时，A 结束后浏览器**不关**，B 直接复用。
