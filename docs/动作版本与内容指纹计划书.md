# 动作版本与内容指纹计划书（v1）

> 状态：待实现（2026-11-01）
> 涉及仓库：`RPA-Browser`（后端）、`Vue3FrontEndDemoExercise`（展示）
> 关联计划书：`docs/fork-上游同步计划书.md`（本计划书**替换其 §2.1 的判定口径**）

## 1. 背景与目标

复合动作（`CompositeActionModel`）目前有两种"版本"相关诉求，但都没有可靠实现：

1. **用户不知道自己在用哪个版本**：`version` 列早在建表时就存在（默认 `"1.0.0"`），
   但 `CompositeActionCreateRequest` / `CompositeActionUpdateRequest` **都不接受它**，
   导出接口不返回它，导入脚本把它当"数据库冗余字段"丢弃。
   结果：`actions/*.json` 里手写的 `"version": "1.1.0"` 从未真正落库。
2. **后端判断不了"是不是最新版"**：现有 `has_upstream_update` 用
   `上游.updated_at > 副本.last_synced_at` 判定（`fork-上游同步计划书.md` §2.1）。
   而 `updated_at` 在改图标、改名、改描述、启用/禁用时都会推进
   （`action_crud.py:647/689/703`），导致上游"只换了个图标"就向所有用户报"有新版本"；
   反之手工改库或批量迁移把时间戳刷平，则漏报（原计划书 §10 风险 1 已承认该缺陷）。

本计划书目标：

- **G1 版本可声明、可传递**：`version` 打通到创建 / 更新 / 导入 / 导出 / 列表 / 详情全链路，
  由作者在"发布"语义下自己维护，服务端**不自动递增**。
- **G2 内容指纹可判定**：新增 `content_hash`（语义内容 sha256），
  让"是否最新"变成**内容相等性**判断，而不是时间戳比较。
- **G3 修复误报/漏报**：`.updated_at` 判定 → `.content_hash` 判定；改图标不再算新版本。

## 2. 核心设计：version 与 content_hash 分工

两者不是替代关系，是**人读**与**机判**的分工：

| 字段 | 来源 | 用途 | 是否自动维护 |
|---|---|---|---|
| `version` | 作者声明（JSON / 前端表单） | 展示、传播、发布说明；用户问"我这是几版" | 否，由人决定 |
| `content_hash` | 服务端按语义内容计算 | 后端判等、Fork 同步判定、跨实例比对 | 是，内容变更即重算 |

**为什么不能只用 version**：

- 用户改了 `steps` 却忘了改 `version` → 版本号声称最新，内容已不同（**撒谎**）；
- 两次不同改动复用同一版本号 → 无法区分；
- 只改名字/图标 → 版本号变了但内容没变。

**为什么不能只用 content_hash**：哈希不可读，用户无法用它沟通"我要 1.2 版那个"。

结论：`version` 给人，`content_hash` 给机器；两者都不自动联动，避免产生无意义版本号。

## 3. 内容指纹（content_hash）口径

### 3.1 参与计算的字段（"语义内容"，全算）

| 字段 | 参与 | 理由 |
|---|---|---|
| `steps` | ✅ | 动作行为本体，最核心 |
| `parameters_schema` | ✅ | 参数定义变化对消费方是破坏性的 |
| `input_vars` | ✅ | 输入变量契约变化同样破坏调用方 |
| `output_vars` | ✅ | 输出契约变化影响下游取值 |

### 3.2 明确排除的字段

`name` / `description` / `icon_series` / `icon_id` / `is_public` / `is_enabled` /
`tags` / `timeout` / `retry_*` / `log_*` / `mid` / `original_mid`。

排除理由是这些属于**展示、可见性与运行时策略**，改它们不应向所有 Fork 用户报"有新版本"。

> 注意：`timeout` / `retry_*` 被排除是刻意的——它们由同步流程一并覆盖，
> 但不构成"内容版本"语义。若后续希望它们参与，只需改 `_HASHED_FIELDS` 一处。

### 3.3 计算方式

```python
payload = {
    "steps": steps,
    "parameters_schema": parameters_schema,
    "input_vars": input_vars,
    "output_vars": output_vars,
}
canonical = json.dumps(payload, ensure_ascii=False, sort_keys=True,
                       separators=(",", ":"), default=str)
content_hash = hashlib.sha256(canonical.encode("utf-8")).hexdigest()
```

要求：

- `sort_keys=True` + 紧凑分隔符 → 同内容必同串，与 dict 插入顺序无关；
- `ensure_ascii=False` → 中文步骤名不产生转义差异；
- 存储 `sha256` 十六进制（64 字符），对外可用短前缀（前 8 位）展示。

### 3.4 Fork / 同步时的特殊规则（关键）

Fork 与同步会用 `_replace_ca_action_ids_in_steps` 把 `steps` 里的复合动作引用
`snowflake action_id` 从"上游视角"改写成"用户视角"。这意味着
**副本的 steps 与上游字节不同，但语义等价**。若副本重算 hash，将永远不等于上游 → 永久误报"有新版本"。

因此：

- **Fork 创建 → `content_hash = 上游.content_hash`（继承，不重算）**
- **同步覆盖 → `content_hash = 上游.content_hash`（继承，不重算）**
- **同步时新建的依赖副本 → 同上**
- **用户通过 `update` 改任一项参与字段 → 重算自身 `content_hash`**

### 3.5 新增快照字段 `last_synced_hash`

`last_synced_at`（datetime）保留不动，继续用于前端展示"上次同步时间"。
新增 `last_synced_hash: str`（默认 `""`）记录"同步时上游的 content_hash"。

判定口径：

```
has_upstream_update =
    forked_from_id 非空
    且 上游存在且 is_public
    且 (上游.content_hash 为空 或 副本.last_synced_hash IS NULL/'' 或 两者不等)
```

`上游.content_hash` 为空（存量未回填）时按"未知版本"处理 → 报一次可同步，
同步后两侧都写入 hash 即进入稳定判定（与旧口径的"存量提示一次"一致）。

## 4. 数据模型变更

`app/models/database/workflow/models.py` → `CompositeActionModel` 新增：

| 字段 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `content_hash` | `str` | `""` | 语义内容 sha256（64 位小写十六进制）；`""` = 未知/未计算 |

但工作流的"语义内容"边界（外壳触发配置 vs 引用动作）需要单独定义，
本期**只覆盖 `CompositeActionModel`**，工作流后续按同一模式跟进。

### 8.2 存量回填（必须执行，否则判定永远为"有更新"）

新增 `scripts/backfill_action_content_hash.py`：

1. 先处理**非 Fork** 动作（`forked_from_id IS NULL`）：按 §3.3 重算 `content_hash`；
2. 再处理 **Fork 副本**（`forked_from_id` 非空）：`content_hash = 上游.content_hash`；
3. 最后把 `last_synced_hash = content_hash`（存量副本视为"当前即最新"，
   避免升级瞬间给所有用户推一条"有新版本"通知）；
4. 支持 `--dry-run` 只统计不写库；输出 `updated/skipped` 计数。

> 顺序不可颠倒：Fork 必须在上游回填完成后继承，否则会把空 hash 继承下来。

## 10. 风险与取舍

1. **version 与内容脱节**：作者改了 steps 不升 version，会出现"内容新但版本号旧"。
   本设计不强行阻止——`content_hash` 会如实反映内容差异，前端展示 `上游内容已变更，
   版本号仍为 vX（作者未升级）` 反而是有用的诊断信息。
2. **JSON 序列化差异导致假性不等**：dict 顺序、浮点精度、`None` vs 缺省字段都可能让
   同语义内容算出不同 hash。缓解：`sort_keys=True` + `default=str` + 统一在
   `create`/`update` 的**归一化之后**计算（与落库内容同源）。
3. **Fork 继承 hash 的前提**：要求所有改写 steps 的地方都走"继承"而非"重算"。
   新增写入点必须核对 §5 表格。
4. **`scripts/import_action_from_json.py` 的 upsert 语义未变**：仍按名字匹配，
   不做"版本比对后拒绝覆盖"。跨实例的版本比对（导出 JSON 里带 origin 信息）
   列为后续项，本期不做，避免改动导出结构破坏既有脚本。
5. **回填脚本必须在上线后立即执行**：未回填期间，所有 Fork 副本显示"有更新"，
   但点同步不会出错（内容本就一致，`local_overwritten` 也不会置位）。
