# 动作版本与内容指纹（前端需求）

> 后端实现与口径见 `docs/动作版本与内容指纹计划书.md`。本文只描述前端要做什么。

## 1. 后端新增/启用字段

### 详情 `CompositeActionDetailResponse` / 列表项 `CompositeActionListItemResponse`

| 字段 | 类型 | 说明 |
|---|---|---|
| `version` | `string` | 作者声明的语义化版本，如 `1.1.0`。列表项本次新增 |
| `content_hash` | `string` | 内容指纹（64 位十六进制）。**展示只用前 8 位** |
| `has_upstream_update` | `bool` | 已有字段，判定口径已改为内容指纹 |
| `upstream_version` | `string \| null` | **新增**：上游当前版本号；非 Fork 或上游不可用时为 `null` |
| `upstream_content_hash` | `string` | **新增**：上游当前内容指纹；非 Fork 或上游不可用时为空串 |

### 请求体

- `CompositeActionCreateRequest.version`：可选，默认 `1.0.0`
- `CompositeActionUpdateRequest.version`：可选，不传表示不修改

## 2. 展示要求

### 2.1 列表 / 详情：版本标识

在动作名称旁展示版本徽标，内容为 `v{version}`，悬浮显示完整指纹前 8 位：

```
参与B站抽奖   v1.1.0 · afd1ed7a
```

- `content_hash` 为空串时只显示 `v{version}`，不显示指纹（存量未回填）；
- 徽标需要带功能级 class，例如 `action-version-badge`、`action-content-hash`。

### 2.2 Fork 副本：上游 vs 本地

`forked_from_id != null` 时，在现有「可同步」徽标旁补充版本对比：

| 状态 | 条件 | 文案 |
|---|---|---|
| 已是最新 | `has_upstream_update = false` | `v1.1.0（最新）` |
| 上游有新版本 | `has_upstream_update = true` 且 `upstream_version != version` | `上游 v1.3.0 · 你的副本 v1.1.0` |
| 内容已变但版本号没升 | `has_upstream_update = true` 且 `upstream_version == version` | `上游内容已更新，版本号仍为 v1.1.0（作者未升级版本）` |

第三种是刻意保留的诊断信息：作者改了 `steps` 却忘记改 `version` 时，
内容指纹会如实反映差异，不应被前端的"版本号相同"掩盖。

### 2.3 编辑表单：版本号输入

- 在动作编辑表单（名称/描述附近）增加「版本号」输入框，`el-input`，`size="default"`；
- 新建时默认值 `1.0.0`，说明文案：`作者自行维护，服务端不会自动递增；判断内容是否变化请看指纹`；
- **不要**在保存时自动 +1，也不要根据是否有改动联动。

## 3. 交互约束

- 点击「同步上游」后，重新拉取详情以刷新 `has_upstream_update` / `upstream_version` / `content_hash`；
- 前端**不得**自行比较 `updated_at` 判断是否有新版本——`updated_at` 在改图标、改名时也会变，
  以后端返回的 `has_upstream_update` 为准；
- 指纹只用于展示与人工核对，不参与任何前端逻辑分支。
